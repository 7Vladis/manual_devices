# ManDev — учёт оборудования и план ТО

Внутренний веб-сервис: справочник единиц оборудования с их составом и
характеристиками, план технического обслуживания со сроками по правилам,
история работ, файлы и комментарии. Умеет зеркалить работы в YouTrack и слать
сводку по приближающимся ТО в Mattermost.

Рассчитан на небольшую команду — несколько инженеров и администратор.

## Что нужно на сервере

- Docker и плагин Docker Compose (`docker compose version` должна отвечать);
- свободные порты 8000 (веб) и 5432 (база);
- доступ к YouTrack и Mattermost — только если эти интеграции нужны.

Больше ничего ставить не требуется: Python, зависимости и база поднимаются
в контейнерах.

## Установка с нуля

### 1. Забрать код

```bash
git clone <адрес-репозитория> mandev
cd mandev
```

Клонируйте под тем пользователем, от которого будете запускать сервис.
Это важно: каталог проекта монтируется внутрь контейнера, и сервису нужно
писать в него `logs/`, `media/` и `staticfiles/`.

### 2. Создать файл настроек

```bash
cp .env.example .env
```

Минимум, который нужно заполнить, — четыре значения:

| Переменная | Что это |
|---|---|
| `SECRET_KEY` | ключ подписи сессий, генерируется командой ниже |
| `ALLOWED_HOSTS` | домены и адреса, по которым открывается сервис |
| `DB_PASSWORD` | пароль базы, придумайте любой |
| `DJANGO_SUPERUSER_PASSWORD` | пароль первого администратора |

Ключ:

```bash
openssl rand -hex 32
```

`DB_HOST` править не нужно: внутри сети контейнеров он подставляется
автоматически. Остальные разделы `.env` — HTTPS, LDAP, YouTrack — снабжены
пояснениями прямо в файле.

### 3. Указать пользователя контейнеров

```bash
echo "APP_UID=$(id -u)" >> .env
echo "APP_GID=$(id -g)" >> .env
```

Обычно у первого пользователя системы это 1000 — ровно то, что стоит по
умолчанию, и шаг можно пропустить. Но если клонировали от root или от
учётной записи с другим номером, без этого контейнер не поднимется: Django
не сможет создать каталог `logs/` и упадёт ещё при чтении настроек.

Проверить, что подставилось:

```bash
docker compose config | grep user:
```

### 4. Запустить

```bash
docker compose up -d
```

Первый запуск занимает несколько минут — собирается образ. Дальше сервис
сам применит миграции, соберёт статику и создаст администратора из `.env`.

Открывайте `http://<адрес-сервера>:8000` и входите по почте и паролю из
`DJANGO_SUPERUSER_EMAIL` и `DJANGO_SUPERUSER_PASSWORD`.

## Из чего состоит сервис

```
db         PostgreSQL. Данные в именованном томе postgres_data.
web        Django под gunicorn, три воркера. Порт 8000.
scheduler  Фоновые задачи. Живёт отдельным контейнером намеренно:
           один контейнер — ровно один планировщик, сколько бы
           ни было веб-воркеров.
```

Планировщик делает две вещи: раз в сутки в 09:00 рассылает сводку по
приближающимся ТО в Mattermost и каждые пять секунд разбирает очередь обмена
с YouTrack. **Если планировщик не работает, обмен с YouTrack просто не идёт** —
комментарии и отметки о ТО сохраняются локально и ждут в очереди. Карточка
объекта честно покажет это пилюлей «YouTrack» в шапке.

## Настройка после установки

Всё остальное настраивается в самом интерфейсе, в разделе «Настройки»:

- **Пользователи** — четыре роли. Младший инженер только смотрит и
  комментирует, старший ведёт справочник, администратор управляет настройками
  и учётными записями, суперпользователь — то же плюс доступ к админке Django.
- **Типы оборудования** и **правила планирования** — на них опирается расчёт
  сроков ТО.
- **Уведомления** — webhook Mattermost для ежедневной сводки.

Токен YouTrack личный у каждого пользователя: кнопка «YouTrack» в правом
верхнем углу. Без него обмен с задачами не работает — сервис ходит в YouTrack
от имени того, кто выполнил действие.

## Обновление

Распакуйте новый релиз рядом с рабочим каталогом и запустите из рабочего:

```bash
./update.sh --dry-run    # посмотреть план, ничего не меняя
./update.sh              # обновить
```

Скрипт перенесёт в новый релиз `.env`, вложения (`media`), логи и сертификат
LDAP, остановит сервисы, поменяет каталоги местами и поднимет всё заново.
Старая версия останется рядом с отметкой времени — на случай отката.

**Базу данных скрипт не трогает и резервных копий не делает.** Снимок базы
перед обновлением снимайте отдельно:

```bash
docker compose exec -T db sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' > backup-$(date +%F).sql
```

Имя базы и пользователя подставит сам контейнер — держать их ещё и в
окружении оболочки не нужно.

## Повседневные команды

```bash
docker compose ps                        # что работает
docker compose logs -f web               # логи веба
docker compose logs -f scheduler         # логи планировщика и очереди
docker compose restart web               # перезапустить веб
docker compose down                      # остановить всё
docker compose exec web python manage.py send_maintenance_digest --dry-run
```

Логи пишутся и в файлы: `logs/django.log` и `logs/app.log`, с ротацией по
10 МБ.

## Если что-то пошло не так

**Контейнер `web` падает сразу после старта, в логе `Permission denied` на
`/app/logs`.** Номер пользователя в `.env` не совпадает с владельцем каталога.
Сверьте `id -u` с тем, что стоит в `APP_UID`, либо передайте каталог нужному
владельцу: `sudo chown -R $(id -u):$(id -g) .`

**`ImproperlyConfigured: Не задан SECRET_KEY` (или `ALLOWED_HOSTS`).** При
`DEBUG=False` эти значения обязательны — сервис намеренно не стартует с
пустыми. Заполните их в `.env`.

**Сервис открывается, но при входе «CSRF verification failed».** Работаете
за HTTPS-прокси: добавьте адрес в `CSRF_TRUSTED_ORIGINS` и включите
`ENABLE_HTTPS=True`.

**Пилюля «YouTrack» в карточке жёлтая, подсказка говорит, что ответа нет.**
Не работает планировщик — проверьте `docker compose ps` и логи контейнера
`scheduler`.

**Пилюля «YouTrack» красная.** Операция не ушла в задачу; наведите курсор —
в подсказке будет причина. Нажатие на пилюлю ставит её в очередь заново.

**`web` не стартует, потому что не поднялась база.** Посмотрите
`docker compose logs db`: обычно дело в том, что том `postgres_data` остался
от установки с другим паролем. Либо верните прежний `DB_PASSWORD`, либо
удалите том командой `docker compose down -v` — **вместе с ним пропадут все
данные**.

## Замечание о безопасности

В `docker-compose.yaml` порт базы 5432 опубликован наружу — это удобно при
отладке, но на сервере, смотрящем в сеть, лишнее. Если внешний доступ к базе
не нужен, уберите у сервиса `db` блок `ports`: контейнеры общаются между собой
по внутренней сети и без этого.

## Разработка

Локально сервис можно поднять без контейнеров — нужна только база. В `.env`
для этого поставьте `DEBUG=True`: иначе Django не будет отдавать статику,
а `ALLOWED_HOSTS` и `SECRET_KEY` станут обязательными.

```bash
python -m venv venv && ./venv/bin/pip install -r requirements.txt
docker compose up -d db
./venv/bin/python manage.py migrate
./venv/bin/python manage.py runserver
```

Проверки перед изменениями:

```bash
python manage.py test                   # прогон тестов
python manage.py makemigrations --check # после правок моделей
python manage.py check --deploy         # с DEBUG=False
```
